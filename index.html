What “60 for 10” actually buys

An advertised “60 for 10” says little about what a plan delivers. This is how we make plans comparable, and every step is reproducible.

1

The provider's own token prices

Every model behind a plan has published API token prices: input, output, cached-read and cached-write. We use them to turn credits or dollar usage into requests.

2

Provider credit formulas

Providers define their own credits (GLM: (in×6.9 + cached×1.7 + out×24)/10000). We take those formulas from the official docs instead of inventing them.

3

Cache-aware workload model

Coding agents hit the cache constantly. We price input as 5% fresh and 95% cached-write, and use the real rates for cached reads and output, per model and workload pattern.

Show all steps
4

Time windows are throughput caps

A 5-hour window is a throughput limit rather than a monthly quota. Weekly credits scale to a month (×4.33), and we never multiply 5-hour caps into monthly numbers.

5

One workload pattern per model family

Some feeds reuse one generic workload pattern. For shared model families we use the most precise per-model pattern for both plans, so neither plan gets a cheaper pattern.

6

Undisclosed numbers stay empty

If a provider does not publish its numbers, we say so. We do not invent credits or back-calculate quotas.

7

Listed prices, plus fees where a vendor adds them

We show the price each vendor lists. Command Code adds a card processing fee to every plan and does not publish the rate, it appears at checkout, so those prices carry a “+ fee” mark. Where a vendor publishes a complete price, we show it unchanged.
